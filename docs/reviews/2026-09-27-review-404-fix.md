## Rulings on the Builder's 3 flagged deviations

### (1) `/foo.bar` still renders `__next_error__`: **ACCEPT the narrow T2 exception. Do not restructure.**

- **The evidence holds.**
  - Status is 404, the Flight stream is fully resolved, and T2 asserts zero dangling rows and no `%%drp:`.
  - There is one `<html>` and `noindex` is present. T1 shows the German title visibly with `lang=de`, and there is no `pageerror`.
  - This is not a recurrence of the defect. The original crashed because rows were never defined. Here every row is defined.
- **The only cheap structural alternative is not available.**
  - That alternative is `generateStaticParams` + `dynamicParams = false` on `[locale]`, which would route an invalid locale to global-not-found. `dynamicParams.md:22` says it is removed under Cache Components.
  - The other option is to make the proxy handle dotted paths. That risks breaking static files, and it costs more than this edge case is worth.
- **Residual cost** (should be recorded in ADR-002; see SHOULD-FIX 4):
  - SSR `<body>` is empty, so no-JS clients see a blank page.
  - The whole class includes real traffic: `/favicon.ico`, `/wp-login.php` and `/apple-touch-icon.png`. Bots and browsers only care about the status, which is correct.
- **Condition on acceptance:** keep the T2 exception keyed to the exact URL `/foo.bar`, as it is now, not a pattern. Any new URL with `__next_error__` must still fail. It does, because `/en/foo.bar` goes through global-not-found and is asserted clean.

### (2) T4 scoped to `meta.status === 404` docs without `postponed`: **ACCEPT. It would have caught the original bug, twice.**

- The original artifact (tech-lead RCA l.58, architect cross-review l.21) was `en/[...rest].meta` with `"status": 404` and **no `postponed` key**, and its `.html` started with `<html id="__next_error__">` and contained `%%drp:`. That document falls inside T4's scope, so both marker checks fire.
- Independently, T4 check 2 (a `[...rest]` route in `prerender-manifest.json` `dynamicRoutes`) would also have failed.
- The narrowing from D3's status-agnostic rule excludes only `_global-error.html` (status 500, `__next_error__` by design). I confirmed that is the only file it excludes on this build.
- Residual gap: a finished status-**200** doc with `__next_error__` would not be flagged. That is a different bug class, and T2/T1 would see it at runtime. The single-`<html>` check still runs for every non-postponed doc.

### (3) T1 "soft nav" uses browser-back and asserts outcome, not softness: **ACCEPT the outcome-only assertion; change the mechanism (SHOULD-FIX 2).**

- My `router.push` probe shows that a client transition to a wholly unmatched URL falls back to a hard navigation, whichever way it is triggered. So "stays soft" is not something to assert.
- The plan's actual case was "from `/en/deals`, navigate client-side to `/en/nope`". `window.next.router` is exposed in production (`next/dist/client/components/app-router-instance.js:387-388`), so the test can drive the real App Router path the plan named instead of `goBack()`. Chromium's bfcache or popstate is a different code path.

## MUST-FIX

1. **T4 is not run by CI.**
   - `.github/workflows/ci.yml` was not changed.
   - `verify:404-build` exists only in `package.json:18`.
   - The plan (D3 / step 1 T4) and ADR-002 decision 5 both count T4 as a gate. As things stand, it is a script nobody runs.
   - **Fix:** in `build-web-next` (after `npm run build`), and/or in `e2e-web-next` after its build, add `- name: 404 build-artifact check (T4)` with `run: cd web-next && npm run verify:404-build`.
2. **T1 omits the P-11 assertions the plan required.**
   - Step 6 says: "T1 asserts the brand bar, both buttons and their `href`s per locale, and asserts that no `<header>`/`<footer>` nav from the main site is present."
   - `e2e/v2-acceptance.spec.ts:216-250` asserts only the title, `lang`, `noindex` and the absence of "Something went wrong".
   - The behaviour is correct today (my curl check above), but nothing protects it.
   - **Fix:** for each global-not-found URL in T1, add these assertions:
     - the visible link `errors.browse_deals` has `href` `/deals` or `/en/deals`;
     - the visible link `errors.back_to_home` has `href` `/` or `/en`;
     - the visible brand link `basketch — home` has `href` `/` or `/en`;
     - no visible main-site nav, for example `getByRole('link', { name: <nav.deals label> })` has count 0.
   - For `/foo.bar`, which is the root `not-found.tsx`, assert its `/deals` and `/` links.

## SHOULD-FIX

1. **Plan step 3 is only half done: downstream props are still `locale: string`, but ADR and comments say the type checker enforces parsing.**
   - Still typed `string`:
     - `VerdictHero.tsx:13`, `StaleBanner.tsx:9`, `ShareVerdictButton.tsx:11`;
     - `DealsClient.tsx:42,342,431`, `deals/page.tsx:57`, `list/page.tsx:50`;
     - `ListDrawer.tsx:23`, `price-block.tsx:9`, `ItemNote.tsx:28`, and others.
   - The plan asked for `Locale` here: "The type checker then finds any caller that skips parsing".
   - These say that guard exists, and it does not:
     - `src/i18n/parse-locale.ts` doc comment ("typing every downstream prop as `Locale` … makes that bug class a type error");
     - ADR-002 § Consequences ("a type error at every downstream call site typed `Locale`").
   - The runtime fix is complete. Every entry point parses, and I grepped `layout` (both functions), `page`, `about`, `deals` and `list` to confirm. The only missing piece is the type-level regression guard.
   - **Fix:** type at least the `Intl`-calling boundaries as `Locale`: `VerdictHero`, `DealsClient`, `price-block`, `ListDrawer`/`fmt`, `ItemNote`/`FromDate`, `lib/share.ts`, `lib/format.ts`, and `getWeeklySnapshot`'s arg. Or reword the comment and the ADR so they do not claim a guard that does not exist. The first is preferred, because it is what the plan specified.
2. **T1 back-nav case: drive `window.next.router.push('/en/nope')` from `/en/deals`** instead of `goBack()`. That is the plan's scenario, and it exercises the App Router's RSC fetch → MPA fallback path. Keep the outcome-only assertions and the recorded finding.
3. **Root `src/app/not-found.tsx` hardcodes its copy.**
   - It hardcodes "Seite nicht gefunden", the body, "Aktionen ansehen" and "Zur Startseite".
   - The plan says the 404 copy comes from `messages/*.json`, and the Designer decision relies on "the same, unchanged strings".
   - `global-not-found.tsx` already shows the pattern: `import deMessages from '../messages/de.json'`.
   - **Fix:** do the same here so the three 404 surfaces cannot drift apart.
4. **ADR-002 residual section: record the real-world reach of the `/foo.bar` class** (`/favicon.ico`, `*.php`/`*.png` probes) and the no-JS blank body. Also drop or qualify "one static, cacheable document per matching CDN edge, with zero function invocations". Nobody has verified it on Vercel yet: that is step 11, post-deploy.
5. **The post-deploy T2 `workflow_dispatch` job (plan step 1 "Infra") is not present.** This is fine if it is deliberately deferred to step 11, but track it with an owner.

## NIT

1. `parseLocale`'s `RoutingConfig` takes `readonly string[]` but returns the app's `Locale` via a cast, so a test routing with other locales gets a lying type. Make it generic like `localeFromPathname`: `<L extends string>(raw: string, routing: { locales: readonly L[] }): L`.
2. `[locale]/error.tsx`: "Reference:" is hardcoded English inside an otherwise localized boundary. Also, `<Link><Button>` nests a `<button>` in an `<a>`, which is invalid interactive nesting. `[locale]/not-found.tsx` uses the same pattern, which predates this change. Consider `buttonVariants` on the `Link`, as `global-not-found` does.
3. T2 has no `x-matched-path` assertion. `next start` does not emit the header (confirmed: absent in my curl), so leaving it out is correct, but add a one-line comment saying so and pointing to step 11.
4. `localeFromPathname` strips `?`/`#` although the caller passes `window.location.pathname`, which never contains them. This is harmless and the tests document it.

## What's well done

- The fix goes after the root cause, not the symptom. It deletes the fallback shell and routes unknown URLs at the routing level, with the doc citation inline in `next.config.ts`.
- `global-not-found.tsx` is properly static:
  - no request APIs;
  - imports only a pure `cva` and an SVG mark;
  - both blocks read from `messages/*.json`;
  - `lang` is set per block;
  - locale hrefs are built in, so no island mutation is needed for links, which is better than the plan's "set by the island".
- `parseLocale` is a clean "parse, don't validate" boundary. Its tests use the real Next digest (`NEXT_HTTP_ERROR_FALLBACK;404`) with no mocks.
- The T3 fixture plus the `gotoStable` global-error check now guard every acceptance test, not just 404s.
- T4 fails loudly on an unknown build shape, as A3 asked.
- `error.tsx` states honestly what it does **not** catch.
- The Builder flagged its own deviations with evidence instead of hiding them.
- No regressions:
  - The route table is unchanged apart from `[...rest]`.
  - vitest 439/439 and tsc are clean.
  - CI's `e2e-web-next` runs `playwright test` with `CI` set, so T2/T1 run against `next start` there (`useProdServer`), and `test.skip` in T2 does not trigger.
  - I did not run the full e2e suite, because data-dependent ACs need Supabase secrets that are not available locally.
