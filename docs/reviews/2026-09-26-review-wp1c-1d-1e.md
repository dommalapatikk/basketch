## 1. WP-1c: products resolve by key set (`pipeline/product-resolve.ts`)

### MUST-FIX

**M-1. `CHUNK_SIZE = 200` counts keys. This codebase has already seen a 200-key `.in()` on product names fail in production.**
- `pipeline/product-resolve.ts:43` sets `CHUNK_SIZE = 200` (a key count). The comment at `:17-20` says this is "the same shape `supabase-classification-cache.ts` already uses". It no longer is.
- `pipeline/transformation/infrastructure/supabase/supabase-classification-cache.ts:40-66` records that `LOOKUP_CHUNK = 200` over raw product names failed in production: "exactly 3 of 8 chunks failed on every attempt of every run … the chunks holding the longest names" (run 34703713179). The fix was a **byte** budget (`LOOKUP_BUDGET_BYTES = 5_000`) plus `LOOKUP_MAX_KEYS = 150`. The file cites the postgrest-js `urlLengthLimit ?? 8000` and the 16KB header hint.
- `source_name` is the same raw name (umlauts, `&`, `%`, spaces, commas that force quoting in `.in()`). Coop sends ~1,500-2,000 names per run, so the same overflow is likely.
- **This failure spreads.** `fetchExistingByKeySet` returns `null` when any one chunk fails (`:98-104`). `resolveProducts` then returns an **empty** map for the whole store (`:135-140`). One oversized Coop chunk means **zero** Coop deals get a `product_id`, on every run, deterministically. The old code resolved everything (by merging).
- Fix: reuse or extract the byte-budget chunker from the classification cache. Retry a failed read like the cache does. Degrade per chunk (resolve the names you could read), not per store. Add a test with long umlaut names that asserts each chunk's encoded length stays under the budget.

**M-2. Two deals with the same `source_name` put duplicate `id`s into one grouped upsert, so Postgres rejects the whole batch.**
- `:165-185` pushes one `offerDateUpdates` entry **per deal**, with no dedupe by product `id`. `resolveProducts` gets the pre-dedupe list (`run-pipeline.ts:402` filters `resolved` by store). Two deals with the same name (a different `valid_from`, or the same-key duplicates that `storeDeals` itself collapses) both queue the same `id`.
- `:288-301` sends them in one `INSERT … ON CONFLICT (id) DO UPDATE`. Postgres rejects any statement that proposes the same conflict key twice (SQLSTATE 21000, "ON CONFLICT DO UPDATE command cannot affect row a second time"). **Proven by probe:** two deals named "Vollmilch 1L" (valid_from 09-24 and 09-25) against one existing row produced the upsert payload ids `["prod-1","prod-1"]`. The temporary probe test was deleted afterwards and git status is clean. That loses up to 100 products' offer dates. The old per-row `.update().eq('id')` tolerated this (last write won).
- The new-product path dedupes (`:234-239`). The update path does not. Fix: dedupe `offerDateUpdates` by `id` (keep the latest `validFrom`, or the last one to match the old behaviour). Test: two deals with the same name are resolved against one existing row, and the upsert payload has distinct ids.

### SHOULD-FIX

**S-1. The regression fake only caps the unpaged read.** `product-resolve.test.ts:213-268`: the `.in()` branch returns every match uncapped. Real PostgREST caps **every** response at `max-rows` (1,000), `.in()` included. Correctness today relies on `CHUNK_SIZE ≤ 1000` together with the unique `(store, source_name)` index. A fake that caps all reads at 1,000 would catch a future `CHUNK_SIZE` above 1,000. The fake also does not model URL length, which is the failure that actually happens in production (M-1).

**S-2. The `ignoreDuplicates` assertion in the cap test is weak.** `:264-267` asserts that no upsert was made **with `ignoreDuplicates: true`** for the target. The old code upserted *without* that flag, so this line alone would pass against the old defect. The test still fails on the old code, but only because of the `productId` and `inSpy` assertions. Assert "no insert-path upsert contains the target, whatever the options" instead.

**S-3. The offer-date upsert still writes `canonical_name`, `category`, `store` and `source_name`** (`:291-299`). The values come from the lookup, so the write is a no-op in steady state. But a hand curation made between the read and the write is reverted, and `updated_at` triggers still fire. The rationale for echoing the NOT NULL columns (`:50-61`) is correct Postgres behaviour. Alternative: an RPC `UPDATE … FROM (VALUES …)`, or accept this and write it down in the plan. It is borderline against §7 "no re-write of canonical_name on existing rows".

### Verified OK
- Insert-only-missing uses `ignoreDuplicates: true` (`:246`), and the log counts the rows `.select()` returned (`:257-267`). The count is DB-confirmed.
- Offer dates use one grouped upsert per 100 rows (`:280-310`). There is no per-row loop, and a failure is counted per batch.
- `product_group` is never sent on the update path.

### SHOULD-FIX

**S-4. One CHECK violation now loses 100 deals' prices, not one row's enrichment, and the property test covers only the image CHECKs.** The old enrichment was a per-row `.update()`, so a row that broke `deals_member_price_names_programme`, `deals_aldi_rule` or `deals_rappen_positive` (`20260911_offer_fields.sql:64-66,119-128`) lost only its own enrichment. **S-5. `UnifiedDeal` lets you write "member-only with no programme".** `priceBasis?` and `loyaltyProgramme?` are independent optionals (`shared/types.ts` UnifiedDeal hunk). `{ priceBasis: 'member-only' }` with no programme compiles, and `dealToRow` then emits `loyalty_programme: null`, which the DB rejects, taking the batch with it. The `store.test.ts:692` test itself has to build its deal with `as Partial<Deal>`. Make it one field, e.g. `priceBasis?: { kind: 'everyone' } | { kind: 'member-only'; programme: string }`. That removes the illegal state instead of relying on belt and braces.
