# RCA: unknown URLs return HTTP 404 but show the "500 Something went wrong" page

- **Date:** 2026-09-25
- **Owner:** Tech Lead
- **Scope:** Root-cause analysis only. No code changed, nothing pushed.
- **Versions:** next 16.2.4 (`cacheComponents: true`), next-intl 4.9.1, react 19.2.4
- **Affected:** every URL the app does not route. That covers `/en/*` and `/de/*` unknowns, unprefixed unknowns such as `/does-not-exist`, unknown-locale paths such as `/xx/foo`, and deep unknowns such as `/en/deals/x/y`. The next-intl proxy rewrites all of them onto the same prerendered `/(de|en)/[...rest]` 404 document.

---

## 1. Reproduction

### Production (`https://basketch.vercel.app`, domain from `CLAUDE.md:22`)

```
$ curl -sI https://basketch.vercel.app/en/does-not-exist
HTTP/2 404
x-matched-path: /en/[...rest]
x-nextjs-prerender: 1
x-vercel-cache: HIT
```

- The body of `/en/does-not-exist` and `/en/settings/hidden` starts with `<html id="__next_error__">`.
- Outside `<script>` tags the body is empty (`<body><div hidden=""><!--$--><!--/$--></div>…scripts…`).
- The server sends no visible content. Whatever the user sees is painted by the client.

### Local production build (`next build && next start -p 4517`)

The failure is identical, and the server log shows nothing: no runtime server error occurs.

| URL | status | `<html>` | flight rows referenced but never sent |
|---|---|---|---|
| `/en/does-not-exist` | 404 (prerender) | `id="__next_error__"` | **`9`, `10`** |
| `/does-not-exist` | 404 (prerender) | `id="__next_error__"` | **`9`, `10`** |
| `/xx/foo`, `/xx` | 404 (prerender) | `id="__next_error__"` | **`9`, `10`** |
| `/en/deals/x/y` | 404 (prerender) | `id="__next_error__"` | **`9`, `10`** |
| `/en/does-not-exist` with a Googlebot UA (bypasses the prerender, renders dynamically) | 404 | `id="__next_error__"` | none |
| `/en/deals`, `/en/about` (control) | 200 | normal | none |

A real browser run was not possible: headless Chromium and jsdom were both denied by the session's permission policy. The client-side step in §3 (step 5) is therefore established from the payload plus the Next/React source, not from a captured browser console line. The Builder's first failing test (§6, T1) captures that console line.

## 2. Evidence

### 2.1 The build prerenders a `[...rest]` fallback shell and caches it as a finished 404

`.next/prerender-manifest.json`, `dynamicRoutes["/en/[...rest]"]`:

```
renderingMode: PARTIALLY_STATIC, experimentalPPR: true,
fallback: "/en/[...rest]", fallbackRouteParams: [{paramName: "rest", paramType: "catchall"}]
```

`.next/server/app/en/[...rest].meta` → `"status": 404`, `"x-nextjs-prerender": "1"`. `.next/server/app/en/[...rest].html` starts with `<html id="__next_error__">`.

### 2.2 The cached document still contains the fallback placeholders

The inline router tree reads `"c":["","en","[...rest]"]` and contains the segment `["rest","%%drp:rest:59e62a4199a418%%","c"]`.

`node_modules/next/dist/server/request/fallback-params.js` (the `createOpaqueFallbackRouteParams` comment) says:

> "if this key is found in the static output, it represents a bug in cache components."

### 2.3 Next itself records the head as partial

`.next/server/app/en/[...rest].segments/_head.segment.rsc`:

```
…["$","$4",null,{"name":"Next.Metadata","children":"$L5"}]…,"isPartial":true,…
```

### 2.4 The unresolved rows are the streaming metadata

These are in the served HTML's Flight data:

```
… ["$","$L7",null,{"children":["$","$8",null,{"name":"Next.MetadataOutlet","children":"$@9"}]}]   ← page OutletBoundary
… ["$","$Lf",null,{"children":["$","$8",null,{"name":"Next.Metadata","children":"$L10"}]}]       ← head MetadataBoundary
6:E{"digest":"NEXT_HTTP_ERROR_FALLBACK;404"}                                                      ← the page's notFound()
```

Rows `9` and `10` are never written, and the stream then ends.

### 2.5 Why Next ships a partial Flight stream

`node_modules/next/dist/server/app-render/app-render.js`, prerender `catch (err)` (around lines 4237-4337):

- `isHTTPAccessFallbackError(err)` → `res.statusCode = 404`.
- It renders `ErrorApp` HTML from `getErrorRSCPayload`, which produces `<html id="__next_error__">` (line 1104).
- It then inlines the **main** prerender's Flight stream. The source comment says so:

  > "This is intentionally using the readable datastream from the main render rather than the flight data from the error page render."

In a `cacheComponents` fallback-shell prerender, that main stream is a PPR static stage whose dynamic holes are halted. The metadata is one of those holes, and it is only ever filled by a request-time resume. This result is stored as a complete 404 with no postponed state, so **no resume ever runs**.

### 2.6 What the client does with it

`node_modules/next/dist/client/app-index.js:280`: when `document.documentElement.id === '__next_error__'` the client calls `createRoot(...).render(...)`, a full client render of the inlined Flight data.

When a Flight stream closes with chunks still pending, React's Flight client rejects them with `Error("Connection closed.")`. The string is present in the shipped chunk `.next/static/chunks/0tzsja57qkkxj.js`.

### 2.7 Why no boundary catches it

`node_modules/next/dist/client/components/http-access-fallback/error-boundary.js`, `getDerivedStateFromError`: it only handles errors whose digest is `NEXT_HTTP_ERROR_FALLBACK;*` and otherwise does `throw error` ("Re-throw if error is not for 404").

The app has no `error.tsx` at any level. The **only** component in `web-next/src` that renders "500 / Something went wrong" is `src/app/global-error.tsx:35-37`. `grep` finds no other producer.

### 2.8 Control: a 404 route without fallback params is fine

`.next/server/app/_not-found.html` is real server-rendered HTML with zero dangling rows. The failure belongs specifically to the `[...rest]` fallback shell.

## 3. Root cause (mechanism, in order)

1. **`web-next/src/app/[locale]/[...rest]/page.tsx:8-10`** is a catch-all page whose only job is to call `notFound()`.
   - `[locale]` has `generateStaticParams` (`src/app/[locale]/layout.tsx:72-74`); `[...rest]` has none.
   - With `cacheComponents: true` (`web-next/next.config.ts:7`), `next build` therefore prerenders a **PPR fallback shell** `/(de|en)/[...rest]` with `rest` as an unknown fallback param (§2.1).
2. At build time that shell's page throws `notFound()` synchronously, which fails the shell render. Next's prerender error path then does three things (§2.5):
   - (a) sets status 404;
   - (b) emits the `<html id="__next_error__">` ErrorApp document;
   - (c) inlines the **main prerender's Flight stream**. Its streaming-metadata holes (`Next.Metadata` `$L10`, `Next.MetadataOutlet` `$@9`) were halted as dynamic, and Next itself marks the head `isPartial: true` (§2.3, §2.4).
3. The result is cached as a *finished* static 404 (`x-nextjs-prerender: 1`, `x-vercel-cache: HIT`) with no postponed state. **Nothing ever resumes it, so the holes stay open forever.**
4. `src/proxy.ts:20` (the next-intl middleware, `localePrefix: 'as-needed'`) rewrites every unknown path onto `/de/...` or `/en/...`. So every 404 on the site is served from this one broken document (§1 table).
5. In the browser, `__next_error__` triggers a client-only render (§2.6).
   - The Flight stream ends with rows 9 and 10 pending, and React rejects them with `Error("Connection closed.")`.
   - Row 10 is rendered inside the head's `MetadataBoundary`, which sits above every segment's not-found boundary.
   - The error is not a `NEXT_HTTP_ERROR_FALLBACK` error, so `HTTPAccessFallbackErrorBoundary` re-throws it (§2.7).
   - There is no `error.tsx`, so it reaches **`src/app/global-error.tsx`**, which shows "500 / Something went wrong" over an HTTP 404.

**Answering the brief's suspects directly:**

| Suspect | Guilty? | Why |
|---|---|---|
| `[locale]/not-found.tsx` | **Not the cause** | Its tree is fully rendered in the payload: `useTranslations` resolved, "Page not found" is present (row `1a`). |
| `[locale]/layout.tsx` | **Not the cause** | It does not throw on unknown segments. |
| `setRequestLocale` | **Not the cause** | It is called correctly. |
| `useTranslations` context | **Not the cause** | See the not-found row above. |
| `[...rest]` catch-all under `cacheComponents` | **The trigger** | Its fallback-shell prerender caches an error document whose Flight data is structurally incomplete. |

The underlying framework behaviour is inlining a halted PPR stream into a cached, never-resumed error document. That is arguably a Next.js 16.2.4 bug; see the §2.2 comment. Next 16.3.6 is `latest` on npm. It is **unverified** whether 16.3.x changes this, so we must not rely on it.

**Confidence:** high on steps 1-4 and on step 5 up to "rows 9 and 10 pending", all directly observed. The exact client error text ("Connection closed.") is inferred from the React source and the shipped chunk. It will be confirmed by T1's `pageerror` capture.

### Secondary defect found on the way (same fix area)

`/_not-found` renders **nested `<html>`**: `<html><head/><body>…<html lang="de"><body …>`.

The cause is that there is no `app/layout.tsx`, so Next injects a default `<html><body>` shell, while `src/app/not-found.tsx:8-9` renders its own `<html>` and `<body>`. This is invalid markup today and will matter once the fix routes unknown URLs to a top-level not-found.

## 4. Why the tests didn't catch it

1. **The test that covers this exact case is skipped.** `web-next/e2e/v2-acceptance.spec.ts:163-164` is `test.describe.skip('AC4 — localized 404')`, with a comment recording it as a "REAL BUG (deferred)". Skipping a known-failing acceptance test removed the only guard. CI runs Playwright against `npm run build && npm run start` (`.github/workflows/ci.yml:149,154`), so an *unskipped* AC4 would have failed in CI: the body contains "Something went wrong" and not "Page not found".
2. **Local e2e runs against `next dev`** (`web-next/playwright.config.ts:50`, `isCI ? 'npm run start' : 'npm run dev'`). Dev mode does not build PPR fallback shells, so this bug class is invisible locally even with AC4 enabled.
3. **No global invariant.** No test asserts that *any* navigation is free of `pageerror` events, or that global-error text never appears. A single fixture-level guard would have caught this, and would catch any future bug that escapes to global-error.
4. **Vitest cannot see it.** The bug lives in build output (prerender, Flight serialization, cache), not in component logic. Component tests of `not-found.tsx` pass and are correct.
5. **Likely history (not verifiable, the repo is not under git here).** The catch-all predates `cacheComponents`. The AC4 note describes an *earlier* symptom: the German root not-found shown on `/en/asdf`. Enabling `cacheComponents` (`docs/adr-M0-decisions.md:188-190`) turned `[...rest]` into a fallback shell and changed the symptom to global-error. Nothing re-tested 404 after that switch.

**System fix (Larson):** skipped acceptance tests need an owner and an expiry. And any e2e check that depends on build-only behaviour (PPR, prerender, caching) must run against `next start`, never `next dev`.

## 5. Fix design (no quick hacks)

### Decision: route unknown URLs at the routing layer and delete the catch-all

The docs for this exact Next version describe our shape as the reason to use `global-not-found.js` (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/not-found.md:53-56`):

> "Your root layout is defined using top-level dynamic segments (e.g. `app/[country]/layout.tsx`)…"

The same doc says global-not-found is "handled at the routing level … Next.js **skips rendering**" (line 47). So there is no layout, no fallback param, no PPR shell, and no Flight holes.

Changes:

1. **Delete `src/app/[locale]/[...rest]/page.tsx`.** It is the component that creates the broken fallback shell. Removing it also removes the `/(de|en)/[...rest]` entries from the prerender manifest.
2. **Enable `experimental: { globalNotFound: true }`** in `web-next/next.config.ts`. The flag exists in this version: `next/dist/server/config-shared.d.ts:763`.
3. **Add `src/app/global-not-found.tsx`.** It is a full document (`<html>` + `<body>`), imports `./globals.css` and the Inter/Geist fonts, and exports `metadata` with a 404 title. Next adds `noindex` automatically.
   - **Locale selection:** use a pure domain function `localeFromPathname(pathname): 'de' | 'en'`. `/en` or `/en/…` gives `en`; everything else gives `de`, the `as-needed` default. It lives in `src/i18n/` next to `routing.ts` and derives from `routing.locales` and `routing.defaultLocale`, never a second hand-typed list.
   - **Copy** comes from the existing `messages/{de,en}.json` `errors.*` keys, so no hardcoded strings can drift from `[locale]/not-found.tsx`.
   - **The spike must decide how the pathname reaches the component.** Either server-side via the next-intl request header or `headers()`, if that is allowed in global-not-found under `cacheComponents` in 16.2.4, or via a small client component reading `window.location.pathname`. Choose whichever keeps the page **statically prerendered with zero dangling rows**; T2 enforces this. Do not guess: verify against the build output.
4. **Keep `src/app/[locale]/not-found.tsx`.** It remains the boundary for real in-segment `notFound()` calls, for example a future `/deals/[id]` with an unknown id.
5. **Fix the nested-`<html>` defect.** Once global-not-found owns unmatched URLs, `src/app/not-found.tsx` only serves `notFound()` thrown by the root layout. `[locale]/layout.tsx:84` is effectively unreachable because the proxy rewrites unknown locales to `/de/…`.
   - Either delete `app/not-found.tsx`, if the spike confirms global-not-found also covers root-layout `notFound()`, or make it render a fragment rather than `<html>`.
   - Decide from the build output, verified by T4.
6. **Also add `src/app/[locale]/error.tsx`, localized.** This is not a fix for this bug, but it matters: today *any* non-404 error anywhere escapes straight to the un-styled, English-only global-error. A segment error boundary keeps header, footer and locale.

### Options rejected

| Option | Reason rejected |
|---|---|
| Wrap the catch-all in `<Suspense>`, or make it `await params` before `notFound()` | This moves `notFound()` into the streamed, resumed part. The status is then committed as 200 (see the status-code note in `not-found.md:13`), which creates soft 404s. That is worse for SEO and for "objectively correct" pages. |
| Add `error.tsx` alone | It hides the symptom by showing a nicer error on a 404. The root cause, an incomplete cached document, stays. |
| Upgrade Next and hope | Worth a separate spike. After upgrading, T1 and T2 decide on evidence. It is not a fix design by itself. If 16.3.x still reproduces, file it upstream with this RCA's §2 evidence. |

**Reversibility:** this is a two-way door. It touches routing files and one experimental flag, and the behaviour is fully covered by T1-T4 below.

## § Cross-review resolution (2026-09-25, after `docs/rca/2026-09-25-architect-404-cross-review.md`)

The Architect's review is accepted in full: the root cause, the proof that the `.meta` has no `postponed` key (it is stored as a finished document, so nothing will ever resume it), and amendments A1-A3. §5 and §6 above are **superseded** by this section wherever they differ.

### New evidence: `/foo.bar` is a real HTTP 500, not a 404

I re-ran the same build with `next start -p 4518`; the server was killed afterwards. The Architect's missed path is worse than predicted:

```
/foo.bar     → HTTP/1.1 500, empty body
             server log: RangeError: Invalid language tag: foo.bar  at Number.toLocaleString  (digest 181957521)
/en/foo.bar  → 404, <html id="__next_error__">, dangling rows 9,10   (same [...rest] bug as §3)
```

**Mechanism:**

1. The proxy matcher skips dotted paths (`src/proxy.ts:26`), so `/foo.bar` reaches `/[locale]` with `locale="foo.bar"`.
2. The layout and the page render **concurrently**, so `[locale]/layout.tsx:84` `notFound()` does not stop `[locale]/page.tsx:18-36`.
3. That page trusts the raw param. It passes `setRequestLocale(locale)` and then `VerdictHero` calls `snapshot.totalDeals.toLocaleString(locale)` (`src/components/landing/VerdictHero.tsx:40`), which throws `RangeError`.
4. `RangeError` is a non-404 error, so the response is a 500.

**Root cause:** the locale is typed `string` and checked in one place (the layout) instead of being **parsed once into a `Locale`** everywhere it enters. The same unvalidated pattern exists in `generateMetadata` (`layout.tsx:31`) and in every `[locale]/*/page.tsx`. This is a separate defect with the same user symptom, so it is folded into this fix. Its step is new (step 3 below).

### D1: locale inside the global 404 → **Architect's design adopted**

- `global-not-found.tsx` is **fully static**: no `headers()`, `cookies()` or `connection()`.
- **Why not `headers()`:** under `cacheComponents` it creates a PPR hole in the 404 document. That is the bug class we are removing, and it relies on an unverified resume on Vercel.
- **Design:**
  - Server-render **both** locale blocks from `messages/{de,en}.json` `errors.*`, each with its own `lang`. German is visible by default.
  - A `'use client'` island `NotFoundLocale` calls `localeFromPathname(window.location.pathname, routing)` and sets `<html lang>` and `data-locale`.
  - CSS shows the one matching block.
  - `<html lang="de" suppressHydrationWarning>`.
- **Accepted UX cost, recorded:**
  - English visitors may briefly see German before hydration. The page is tiny, so it will usually not be noticed.
  - With JavaScript off, both languages show.
  - The page is `noindex`, so there is no SEO cost.
- If the PM rejects the flash, the only alternative that avoids the same bug class is a neutral bilingual page with no switch. That is a PM call, not a technical one.

### D2: `app/not-found.tsx` → **keep it, render a fragment** (Architect's position)

- The "delete it" branch is dropped.
- `notFound()` from `[locale]/layout.tsx` (reachable via `/foo.bar` once step 3 stops the 500) is caught by the root-level not-found boundary. `global-not-found` is wired only into `/_not-found`.
- Remove `<html>`/`<body>` from the file: Next supplies the shell, because there is no root layout. This fixes the nested-`<html>` defect.
- T2 on `/foo.bar` settles it by evidence.

### D3: T4 → **keep, fail loud on unknown shape; T2 is the primary gate**

- T4 asserts `prerender-manifest.json` `version === 4` and that the expected files exist. If either fails, it fails with the message "Next build-artifact format changed; update this check for Next <version>". It never passes vacuously.
- Generalised rule: no prerendered `.html` whose `.meta` lacks `postponed` may contain `%%drp:` or `id="__next_error__"`.
- T2 parses served HTML only, so it is version-independent. It is the gate; T4 is defence in depth.

### D4: header/footer on the global 404 → **decided by PM (P-11, `docs/decisions/2026-09-25-pm-decisions.md:19`)**

- **Simple page:**
  - a basketch brand bar;
  - "Page not found";
  - two localized buttons ("See this week's deals" → `/deals` or `/en/deals`; "Home" → `/` or `/en`);
  - DE or EN to match the link.
- No full Header/Footer.
- **Open copy question for the PM (not decided here):** P-11's button wording differs from the existing `errors.*` messages:

  | Locale | `browse_deals` | `back_to_home` |
  |---|---|---|
  | en | "Browse deals" | "Back to home" |
  | de | "Aktionen ansehen" | "Zur Startseite" |

  The page must take its copy from `messages/*.json`, not from hardcoded strings. So either the PM confirms the existing keys, or the Builder updates those keys (and the `[locale]/not-found.tsx` copy changes with them). The Builder needs that answer before step 6, and the German wording for P-11 comes from the PM.
